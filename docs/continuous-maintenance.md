# Keep behavior aligned while you ship

After a repository adopts `moldea`, durable project knowledge can stay current as you plan and develop ordinary software or runtime agents. Direct context requests and declared relationships establish relevance; you should not need to append “and update moldea” to those requests.

> **You**
>
> Add manager approval to refunds over $500.

The coding agent checks known implementation paths against declared relationships. If an authorized implementation change makes a selected context file or instruction mirror inaccurate, the coding agent updates it in the same change. A lasting code change alone does not justify searching unknown context. If implementation later reveals a materially new path, it checks that path at an existing scope checkpoint and carries any newly matched owner into completion. It does not repeatedly check unchanged paths or announce `moldea` on a miss. A proposal recorded before its implementation exists matches no relationship when that implementation is first written; ask for the context update explicitly, or declare an impact path for the planned location when the proposal is recorded.

## Maintain project knowledge from conversation

Concrete project facts, approved policies, clear corrections, and project-context questions can establish relevance without special wording:

> **You**
>
> The current ownership boundary is outdated: Platform owns the application runtime and delivery pipeline. Security approves production access.

The same information can arrive as YAML or JSON, a focused answer, or an accessible project source. Format alone does not establish relevance or write authority. The project-level meaning must already be clear from the conversation; a task-local code requirement, uncertain table, or pasted suggestion is insufficient. The coding agent reuses current adoption evidence or runs the bundled adoption-only gate. A miss does not authorize discovery, initialization, or repair. Explicit setup checks retain their bounded diagnostic route.

After adoption, the coding agent reuses known owners or bounded content-free inventory and reads only the smallest relevant content. Informational handoffs, feedback reviews, and read-only planning remain read-only. An unambiguous correction to established project truth authorizes the minimal update to its existing canonical owner without another permission request. New facts go to their area's focused owner. If the area has no owner, the coding agent proposes a focused file, its routing link and any evidenced relationships for approval. A selected policy is not proof of implemented behavior. Unchanged facts and owners are reused, and new information does not reset the shared resource limits.

A pause, narrower request, or topic change stops the pending context writes. If a consequential ambiguity remains, the coding agent asks one focused question before changing context. It keeps temporary status, speculative policy, secrets, personal data the contract does not need, generic engineering knowledge, and facts it can cheaply and reliably rediscover out of canonical context.

When a new claim materially conflicts with established context, its format or bare assertion does not authorize replacement. The coding agent proceeds only when you clearly identify a correction or reliable evidence resolves the conflict; otherwise it asks one focused question that distinguishes whether the claim replaces current state or describes a proposed or future state. It writes nothing before the answer. After an explicit correction, the completion report states the corrected boundary and resulting current truth without unnecessarily repeating obsolete wording. An explicitly read-only request remains read-only, and incidental knowledge never initializes an unrelated repository.

## Reconsider does not mean rewrite

An impact path, explicit knowledge-maintenance request, or semantic relationship means “inspect this surface,” not “edit this file.” Scope matches are candidate authorities, not a requirement to read every owner or every asset. The coding agent selects the smallest affected owner set and prefers an exact task-specific relationship over an overlapping broad glob unless evidence shows both contracts change. If supplied information is not suitable for persistence or existing project context, declared behavior, and evidenced relationships remain accurate, the right result is no `/moldea/**` change.

During ordinary maintenance, the coding agent adds or corrects relationships only for owners whose canonical content the task changes, using already-inspected source that materially governs that content. An established missing or incorrect relationship for a changed owner is part of that update. Merely assessing an accurate owner during code work leaves its prose and manifest declarations unchanged; at most the report notes an established gap in one line. It may correct or remove an existing declaration made invalid by a file move or deletion in the same task, without adding new relationships. Read-only work reports gaps without writing. Initialization registers evidenced new content, while explicitly requested relationship maintenance and repair keep their own scope. A binding already establishes relevance and need not be repeated as an exact impact path. An impact path calls for checking whether the owner's facts still hold or its rules are followed. Use a specific enforcement point, governing project-owned model asset or directly governed authored deliverable. See the [repository format](/docs/repository-format/) for eligibility and path syntax. The coding agent does not scan for candidate paths. It reuses completed scope evidence for relationship-gated work without another inventory call; direct context and repair retain their existing bounded metadata routes. Incomplete evidence is reported as a limitation, not proof of missing coverage. A relationship does not require a new agent or binding, and zero relationships remain valid when none are grounded. The coding agent carries every selected owner, mirror, and outstanding criterion through planning, implementation, and host context compaction. At completion it checks the final state and diff against the authorized outcomes, constraints and paths, and compares final behavior with each selected owner and mirror. The coding agent preserves accurate and unrelated content. If an agent's bound file or known loader, schema, or tool path changed, it checks that agent's actual instruction connection and runs an existing focused test. When it assesses a binding, it names the owner, declared file and export when present, and what the change establishes. Native checks still apply. After canonical writes, it validates the final state. Structural validity alone does not prove semantic alignment.


When neither facts nor evidenced relationships need correction, the completion report identifies the canonical state reconsidered, states that no canonical change was required, and explains why it remains correct. This avoids noisy documentation churn while still preventing silent drift.

## What can be synchronized

Depending on the change, maintenance can reconsider:

- project and focused context
- accepted decisions
- canonical routing descriptions and instructions
- Agent Skill authoritative sources, activation, workflows, references, scripts, assets, host metadata, installed or distributed copies, and consumers
- runtime construction and routing metadata
- schemas, tools, and skills
- bindings and broader impact paths
- exact instruction mirrors
- implementation, tests, and directly affected documentation

## Keep accumulated context organized

`project.md` stays a light entry point explaining purpose, users, goals, and boundaries, with descriptive links to focused owners or topic indexes. Around 32 KiB for the entry point and 128 KiB for a focused document are readability review points. Keep cohesive owners intact at any size.

Keep one focused owner for each product area, policy domain or subsystem. Link to facts owned by another document. Run **Fix moldea** routinely and after large changes to catch misplaced facts, mixed responsibilities, missing routes and incorrect relationships. The agent proposes structural changes, and Maintain applies approved moves without changing their meaning.

You can authorize broader context compression naturally:

> **You**
>
> Consolidate the duplicated project context so each durable fact has one authoritative owner. Preserve current facts and constraints, update references, and leave implementation unchanged.

This is a Maintain operation. Similar wording alone does not establish duplication. The coding agent keeps current truth, plans, history, rationale, and unresolved state distinct. It can consolidate proven duplicates, move facts to established owners, split mixed-responsibility documents, remove superseded wording, and update manifest paths and directly affected references, consumers, and docs. It preserves distinct current facts, accepted rationale, current constraints, unresolved boundaries, relationships, and consumers. If two sources make consequential conflicting claims, the coding agent identifies the conflict and waits for the answer to one focused question before editing.

Compression is limited to repository-owned context. It does not manage host context windows, conversation compaction, prompt caches, token budgets, or model internals, and it does not claim token savings.

## Learn a named area

Ask **Help moldea learn the billing area** to run one evidence-backed round rather than a broad audit. The coding agent shows coverage, agent status, changed files and gaps, then offers up to five numbered proposals. Accept all with **yes**, answer by number, or **skip**. Only confirmed rules, decisions, relationships and routing are saved. Final validation follows the last write.

## Adoption remains explicit

The README may select the entrypoint before relevance is known. Further `moldea` work requires direct project relevance, including project-context questions and project-grounded skill work, an explicit operation, canonical or managed-README work, or a declared relationship. The managed-block boundary limits `moldea`-specific maintenance; it does not prevent documentation changes independently authorized by the host task. Selection does not adopt `moldea` or authorize persistence. Initialization requires explicit developer intent, and adoption is established only by the complete canonical contract.

If the developer prohibits corresponding `moldea` changes, the coding agent respects that scope, completes the authorized implementation, reports likely drift, and does not claim alignment. If an explicit `moldea` request targets an unadopted repository without authorizing initialization, the coding agent does not persist the knowledge and explains that initialization remains a separate explicit operation. Unrelated work receives no adoption recommendation or `moldea` report.

After synchronized writes, each bundled CLI invocation runs as a separate process from project checks, mirror comparisons, and Git inspection. The completion report names the deterministic operation or proof stage when material, its status, and material diagnostics or mirror findings established by that completed process. It does not need to repeat the literal invocation. A generic success claim, failed aggregate command, or unverified response is not sufficient evidence.

When an Agent Skill copy, consumer, or related application belongs to another Git repository, each repository keeps its own authority and verification boundary. The report names every repository's observed current state as changed, unchanged, uninspected, or blocked and separates related evidence from facts local deterministic inspection cannot observe. It reports actual state, not a promise about what it would preserve later. A scope-only direction with no actual semantic change produces no invented work; the coding agent reports the repository states and asks one focused question. Coordinated changes are non-atomic, and a change on one side never proves the other side is complete.
