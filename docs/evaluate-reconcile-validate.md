# Check alignment and correct established errors

## Evaluate

Use evaluation when you want a read-only assessment of project, Agent Skill, and agent alignment:

> **You**
>
> Evaluate the refund agent and do not change repository files.

The coding agent uses deterministic metadata or structural inspection only when it can change the conclusion, verifies every machine envelope it does use, and directly reads only relevant canonical state, Agent Skill sources, host metadata, consumers, implementation, contracts, tests, runtime wiring, file and export coverage, developer intent, and unresolved state. For a direct named reconciliation conflict, it compares supplied or focused implementation evidence with at most one canonical instruction body. It may then read one independent governing source already identified by the task or earlier evidence, within the existing output budget, when that source could settle the exact conflict. Otherwise it asks one focused authority question before further inspection, validation, canonical reads, or any write. Discovery alone does not justify an absence claim or a request to paste an accessible file.

In an adopted repository, `Evaluate the current moldea project.` explicitly selects the repository's canonical system and its material implementation relationships. Natural agent-review requests also activate without naming `moldea`; a generic project review still needs relevant paths. Neither request silently becomes an audit of the installed operating skill. Explicit requests to evaluate a project-owned Agent Skill assess its sources, resources, consumers, and runtime registration within that scope.

The report concisely identifies its starting scope and any material relationship that expanded it, then separates deterministic diagnostics, confirmed semantic problems, material ambiguities, relevant unresolved requirements, and evidence limitations. The assessment checks evidenced implementation relationships for selected owners even when their prose remains accurate. Relationship-gated work reuses completed scope results without a follow-up inventory call; other metadata reads remain bounded by the selected operation. Incomplete evidence does not prove missing coverage. A relationship proves scope, not semantic agreement. The coding agent claims alignment only after reliable evidence establishes material behavior, intended meaning, and relevant consumption. It does not need to narrate every file read or repeat literal commands. Each material runtime limitation names the unknown fact, the smallest reliable resolving artifact and established owner, and what the artifact must prove; unknown ownership stays explicit. Reliable resolvers include source-owned target documentation, closed wiring, provider configuration, and integration tests. For routing metadata, an absent optional handoff description with a consumer of the canonical agent description is an aligned fallback. Under dynamic wiring, the report separates consumer purpose, required canonical source, selected source, and resolving evidence. When selection remains unknown, conclusions stay conditional instead of calling a candidate source current, effective, absent, or wrong. The report explicitly states that no repository files changed.

The report first identifies the project as adopted or unadopted. Concrete diagnostics, drift, conflicts, requirements, and evidence limitations remain separate, and project status is only adopted or unadopted.

## Reconcile

Use reconciliation when you want confirmed drift corrected:

> **You**
>
> Reconcile the refund agent with the current implementation.

Reconciliation begins with the same evidence model, then completes an intended-state gate before editing. Permission to reconcile does not authorize choosing between unresolved policies. Code proves implementation and instructions declare model-facing behavior, but neither selects intended policy. For a consequential same-scope conflict, the coding agent names the exact claims and the evidence role of each. An accepted decision record or identified canonical owner can resolve them only when its governing role is established and its content explicitly settles the dispute. Location, recency, tests, mirror agreement, and repeated claims are insufficient. The coding agent searches for no new resolver after the conflict and changes nothing when the identified source is missing or inconclusive; it asks one focused question instead.

The resulting correction is the smallest coherent change across all genuinely affected canonical, Agent Skill source, resource, metadata, copy, consumer, runtime, implementation, schema, test, mirror, and documentation surfaces.

## Validate

Use validation for deterministic repository-format and declared runtime checks:

> Validate the `moldea` project.

Validation runs the root-local CLI through the installed skill's closed launcher. It checks repository structure, declared files, explicit TypeScript or JavaScript ESM exports, and coding-agent integration. Proven missing files or exports are errors. Unsupported or inconclusive export checks remain not checked; coverage never claims runtime wiring. Operational failures reject the complete operation. A structurally invalid result is completed diagnostic evidence. Validation does not prove instruction usefulness, runtime consumption, or semantic alignment.

Standalone validation with eligible installed tooling does not run a repair Git checkpoint, install dependencies, or enter corrective repair. A repair-helper limitation does not turn a separately requested validation into repair. Bounded no-CLI diagnosis applies when adoption or tooling blocks the check, rather than to every read-only operation.

If adoption misses, fails, or is unavailable during an explicit setup check, the coding agent inspects only bounded canonical foundation excerpts without writes. README drift does not prevent adoption or CLI validation. Core reports a missing or stale AGENTS.md bridge or installed skill asset as an integration warning. It follows a linked AGENTS.md to its target file inside the repository, reports a Claude Code instruction file that does not load AGENTS.md, and reports a link that doesn't lead to a file in the repository with its reason. The coding agent separately smoke-tests the displayed gate with `--diagnose --path README.md`; a completed unrelated `0` is healthy.

## Resolve a warning

Ask to fix the cause, or explicitly accept an eligible supported warning with your own reason. The skill offers integration acceptance only for shared Git-tracked instruction subjects; local fallback and ignored files receive the fix or exact handoff. This is skill policy, not a Core limitation on accepting an absent subject's matching warning. Acceptance matches its exact `code`, `subject`, and `qualifier`, retains the finding, and does not change errors. It becomes unmatched when that diagnostic identity is no longer reported after a completed check; file absence alone does not determine the result. The coding agent does not choose acceptance or invent your reason. After the cause is fixed, remove an unmatched acceptance and validate once more. When AGENTS.md is protected, repair provides the exact installed block for a separate instruction update. Local observations and expected committed/cloud behavior are reported separately, without changing your ignore or tracking rules.

## Repair a project

When the existing setup appears wrong, ask:

> **You**
>
> Fix moldea.

No special syntax is required. The coding agent inventories every owner, checks its material facts and declared relationships, and traces each agent's canonical instruction and schema to its runtime call. Presentation details and shared infrastructure used by a feature do not create feature relationships. It corrects errors whose intended result is established, runs the relevant checks, and leaves healthy state unchanged.

Repair can correct an established damaged foundation or managed document with the required authority. It preserves unrelated bytes and never initializes a new project implicitly. AGENTS.md is changed only when host instructions permit; otherwise the developer receives the exact block and an explanation that adding it matters for ordinary context maintenance. Existing tooling recovery and unresolved-policy safeguards still apply.

During explicit repair, the bundled `repair-git.mjs` helper captures checkpoint, continuation and written-file review evidence. It inspects attributes before status or diff and conservatively refuses any attribute file that mentions `filter`, including Git LFS declarations, and unverified attribute fallbacks. That refusal is a helper limitation, not evidence of an unsafe repository. The helper never fetches missing objects or contacts a remote; an object missing from a partial clone is reported as unavailable evidence. During repair, the coding agent uses this helper for Git evidence, including preliminary configuration lookups and full commit-object verification, and never runs Git directly. Git writes and publication stay with the host. The fixed invocations and limitation handling are in the installed `references/project-repair.md`.

The result separates **Checked**, **Fixed**, **Verified**, **Needs input**, and **Not checked**. Large projects are checked progressively with bounded output. Repair reads moldea documents directly as regular files, never through a symbolic link or a path with a reported problem, and counts those reads and their bytes against its limits. At a limit, the report gives the number of owners checked, source commit, next owner, uncommitted paths, and uncommitted manifest owner entries. The helper captures the full commit from hardened status and explicitly reports repositories without an initial commit. A later repair must establish current coverage before reporting completion. Semantic continuation checks combine actual wrapper invocation records and known disallowed command syntax; they measure [cooperative compliance](/docs/semantic-evaluation/#cases-and-coverage), not resistance to deliberate evasion. Checkpoint availability does not establish tooling eligibility, native read coverage, owner assessment, or reassessment. When the commit is unavailable or checkpoint evidence is incomplete, every completed owner requires reassessment, and any left unassessed is reported as not current under **Not checked**. If a limit or missing evidence prevents complete coverage, the report names what remains and never calls the project healthy. A resource failure preserves earlier corrections as unverified. Pagination does not split source parsing, and repair does not automatically rewrite or split healthy source to clear a limit. Deterministic tooling trials verify installation and launcher mechanics; model-trial outcomes and their assurance limits remain separate evidence.

Structural validity is not proof that every runtime behavior works.

## Quick comparison

| Need                                            | Operation | Writes | Semantic assessment                                                   |
| ----------------------------------------------- | --------- | ------ | --------------------------------------------------------------------- |
| Check repository-format structure               | Validate  | No     | No                                                                    |
| Investigate structural and behavioral alignment | Evaluate  | No     | Yes                                                                   |
| Correct established drift                       | Reconcile | Yes    | Yes                                                                   |
| Check and repair the existing project setup     | Repair    | Yes    | Every completed owner and agent connection; incomplete scope reported |

Repair reports name the actual checks and material gaps for their scope. Reports distinguish structural checks from static alignment within the assessed scope. When an agent or runtime is in scope, they also separate instruction consumption from untested live behavior. A setup without agents or runtimes, or a documentation-format repair, can report its scoped checks without an unrelated live-behavior disclaimer; structural validation alone never establishes project health.
