# Semantic evaluation

Semantic evaluation tests whether a coding agent applies the portable skill correctly in realistic repository tasks. It complements deterministic tests, which prove schemas, generated files, command contracts, and resource boundaries without model execution.

## Isolation and bounded evidence

Actor and judge stages run in isolated homes. Related repositories and evaluator-owned controls are mounted read-only. The runner snapshots the working repository and Git control state before and after actor execution, checks related mounts for changes, and removes its temporary workspace after the trial. The fixed host policy permits task-owned response checkpoints in the sandbox's private `/tmp` directory, including creation, reads and cleanup; it still prohibits access to other temporary files, evaluator-home state and authentication. This uses the existing private mount, without exposing host temporary storage.

Launcher recognition accepts the sandbox Node executable at `/opt/node` and repository arguments that normalize to `/mnt`. Launcher-shaped misses retain only `unrecognized-node-path` or `unrecognized-launcher-path` counts, never the rejected paths. These diagnostics grant no CLI execution credit and do not change security or repair-Git decisions.

Raw command text and output are not recorded. The host projects bounded command-policy counts, exact bundled relevance-gate, managed-README-writer, and managed-AGENTS-helper results, recognized `moldea` operations, aggregate output sizes, and reported token usage. Gate and managed helper results remain separate from `moldea CLI` call counts. Each runner-authored developer request, including `continue`, starts one maintenance cycle with the existing output, command and token limits. Codex reports cumulative token counters when a session resumes; the runner subtracts the preceding session counter before applying per-request token limits or charging that invocation. Missing or inconsistent continuation counters stop execution rather than granting a fresh allowance. Actor-authored reset claims do not start a cycle. Every cycle is checked independently against the 1,625,000-token operating threshold and 2,097,152-token absolute ceiling. A single-request trial and the first cycle count input plus output, including cached input. Resumed cycles count only uncached input plus output (`inputTokens - cachedInputTokens + outputTokens`) for both limits, so re-reading cached session history does not consume their grading allowance. A token overage is retained as that trial’s resource failure, not rejected as malformed evidence or used to stop the campaign. Campaign admission and usage totals still count all reported input plus output, including cached input. Missing cycle usage cannot establish a passing resource result. A failed earlier cycle remains failed even when later requests succeed. Session totals may exceed one cycle’s allowance. Temporary-storage and free-space limits still cover the running operation. Operational failures receive one bounded retry. Semantic (including strict repair-Git) and resource failures, separately or from the same activation, receive confirmation trials when command policy, repository control, mount integrity and operational execution pass. Each trial retains its actual failed dimensions; confirmations never turn a resource breach or noncompliant repair-Git trial into a passing trial. Safety and integrity failures remain hard failures.

### Resource accounting

Protocol 54 grades each cycle on moldea's own work. The host classifies every completed command without retaining its text:

| Command or output                                                  | `ordinary`                                                                      | `largeTraversal`                                                      |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `moldea` launcher call                                             | Host commands, peak and visible output; aggregate `moldea` output; one CLI call | Same                                                                  |
| Bundled helper, including the relevance gate and repair Git helper | Host commands, peak and visible output; aggregate `moldea` output               | Same                                                                  |
| Read, search or shell write under `moldea/`                        | Host commands, peak and visible output; aggregate `moldea` output               | Same                                                                  |
| Any other read, including `README.md` and `AGENTS.md`              | Not counted                                                                     | Host commands, peak and visible output; not aggregate `moldea` output |
| Project tests, builds, Git and package-manager commands            | Not counted                                                                     | Not counted                                                           |
| Codex patch writes                                                 | Not commands                                                                    | Not commands                                                          |
| Model tokens                                                       | Whole cycle                                                                     | Whole cycle                                                           |

Each scenario's `moldea` call and output budget still counts only launcher calls and their output, so a zero-budget abstention case may run the relevance gate. The profile's aggregate `moldea` output allowance, 512 KiB for `ordinary` and 1 MiB for `largeTraversal`, is graded per cycle on launcher output plus helper and `moldea/` output. A command whose owner is unclear, such as an unparseable command that mentions `moldea/`, counts toward the highest owner it could reach. The runner's absolute whole-stage ceilings remain failure containment.

In an ordinary cycle, one final `validate` call is exempt from the aggregate allowance, and from the scenario's call and output budget when it is what crosses them. The ordered Codex event stream must show a patch touching `moldea/` before it, no other validation since that patch, and no later patch to `moldea/` or moldea-owned command. Its output must fit one 65,536-byte page, and the cycle's net changes must still include `moldea/`. A patch whose paths cannot be read may have touched `moldea/`, so the validation must also follow it, but it never earns the exemption on its own. A validation that cannot be matched to a captured launcher call, writes made only through shell commands, and every `largeTraversal` cycle get no exemption. Whether coding agents follow this exception, and whether they choose the correct Yarn installation command, is not evaluated by a scenario.

Recording and diagnostic batches complete every selected initial trial before starting case resolution. Cases run concurrently within both phases. During resolution, each eligible case runs its confirmations sequentially until it reaches the shared quorum; cases do not wait for a global confirmation round before continuing.

Private checkpoints live at `.evidence/semantic/checkpoint.json`. Matching recording and diagnostic-batch commands retain their attempt identity, ordered completed-case prefix, out-of-order worker results, completed trials, and current actor or judge boundary. An interruption during the initial phase starts no confirmations. An interruption during resolution preserves the complete initial set and every durably recorded confirmation, although concurrently resolving cases may have reached different confirmation indices. Resume skips completed trials and durable actor sessions awaiting a judge. An operationally incomplete actor sequence restarts with a fresh fixture and session, retaining completed-cycle evidence and all prior charges; it does not replay a prefix into the interrupted workspace. Malformed or incomplete judge JSON is an operational failure inside the same bounded retry path. Every actor and judge invocation receives a durable charge before it starts. Reported input plus output replaces the conservative absolute host allowance when parsed; cached input remains part of input and is not counted twice. Malformed judge assessments retain parsed usage and command-policy observations before retry; a later clean response cannot erase an observed policy violation. Interrupted calls without usable usage keep the absolute allowance. Per-invocation charges survive session restarts, and campaign admission never resets at a cycle boundary. No verdict is fabricated. A model stage receives one automatic retry; after that retry is exhausted, `--resume-stopped-stage` authorizes exactly one additional call. Use `--restart` to discard the checkpoint instead. An identity mismatch is rejected. Completed local bundles live below `.evidence/runs/semantic/`. The runner considers at most the newest 64 local bundles for exact reuse. A passing case reuses its initial trial; a recovered case reuses its failed initial and passing confirmation quorum. Host commands, prompts, fixtures, case definition, portable artifact, CLI identity, protocol, resource profiles and projected actor evidence must match. Judge prompts use the same canonical JSON serialization as stage identities, so loading validated records cannot change prompt bytes through property ordering alone. Marking a case private removes it from the recording selection without invalidating other cases; changing one case invalidates only that case when all shared inputs stay identical. An unchanged failed case stops before model execution. A case-only correction invalidates that case while preserving other exact passing and recovered cases; this requires a new recording, not resuming a mismatched checkpoint. Public bundles are not backups for this private resume and reuse state.

Current private records use evidence schema 15 and checkpoint schema 3; incompatible private versions are rejected. Historical published bundles remain immutable and are not assigned invented request cycles.

Completed diagnostic batches atomically archive that checkpoint under `.evidence/semantic/diagnostics/<attempt-id>/checkpoint.json` before deleting active state. Both passing and failing batches retain their complete initial/confirmation trials, failure dimensions and paid usage for triage. An archive write failure preserves the active checkpoint for finalization without another model call. These archives are private, are retained through the campaign handoff, and are never official release evidence or reusable recording trials.

After external termination, in-flight calls may have no durable usage record. Before an authorized resume, separately reserve the absolute per-stage token allowance for each such call; the retained checkpoint counter alone does not include them. Preserve the interrupted checkpoint and its inputs. Paid follow-up with a changed evaluator requires a fresh reviewed candidate and separate permission.

Launch long paid batches from an independent terminal rather than a coding-agent command session. On Linux, a detached process with redirected standard streams is another option; record its exact PID, log and exit status, and verify detachment with a nonpaid lifecycle check first. Session detachment does not remove stage timeouts, token admission or resource limits, and does not establish the cause of an earlier SIGTERM. Use the existing resume support only with unchanged frozen inputs and separately accounted interrupted usage.

Before starting a diagnostic candidate, record its HEAD, preflight identities, exact ordered case selection and host settings, and a content fingerprint of evaluator source, fixtures, and execution configuration, including relevant uncommitted and untracked files. Preserve the archive and backup directory exclusions. A checkpoint identity does not by itself bind every judge-prompt or fixture-setup change, so resume only after comparing current input contents with that run-start fingerprint and confirming the same selection and host configuration. Preserve a checkpoint whose original inputs are unknown or changed; do not silently restart it, delete it, or combine its results with a changed evaluator. A stopped-stage extra call needs its explicit command flag and authorization.

## Deterministic inspection

The preflight inspects current definitions and identities and builds every discovered actor prompt without preparing workspaces or starting a model host:

```bash
npm run eval:semantic:preflight
```

Local completed bundles can be revalidated without model execution:

```bash
npm run eval:semantic:verify
```

These commands do not establish new behavioral assurance. They only inspect the current suite or previously recorded local data.

## Diagnose and record

One case can be run without recording:

```bash
npm run eval:semantic -- --case <case-id>
```

This targeted command does not create a candidate checkpoint. If it is interrupted, rerun the case from the beginning.

Bounded diagnostic batches accept exactly one selector:

```bash
npm run eval:semantic:diagnose -- --all
npm run eval:semantic:diagnose -- --cases <comma-separated-case-ids>
npm run eval:semantic:diagnose -- --claims <comma-separated-claim-ids>
npm run eval:semantic:diagnose -- --unresolved-from <attempt-id>
```

Diagnostic batches use the same worker and recovery controls as recording:

```bash
npm run eval:semantic:diagnose -- --all --workers 2
npm run eval:semantic:diagnose -- --all --resume-stopped-stage
npm run eval:semantic:diagnose -- --all --restart
```

Recording writes a complete local attempt and preserves actual failed outcomes:

```bash
npm run eval:semantic -- --record --workers 4
npm run eval:semantic -- --record --resume-stopped-stage
npm run eval:semantic -- --record --restart
```

Worker counts are limited to 1, 2, or 4. Concurrent workers reserve the absolute next-stage token allowance before each model call, and the complete candidate stops before it could exceed 64,000,000 paid tokens. Semantic failures do not stop the remaining cases. Successful recording removes the checkpoint and stores a self-contained local public bundle with its exact case definitions, trials, replay, downloadable evidence artifacts, version, date, and provenance. No command runs automatically as part of website generation.

## Website and release use

The website never loads current case modules. It renders only the semantic bundle selected in `evidence/selection.json`, so adding, editing, or removing current cases cannot change an older selected snapshot. Failed official evidence can be published and selected for an honest public result, while release assurance still requires a passing official bundle.

See [Release evidence](/docs/release-evidence/) for packing, publication, selection, and preparation.

## Scenario boundaries

`exact-binding-relevance` supplies the real before-and-after source change in the request, so an ordinary bounded review does not require guessing the sandbox's undisclosed hardened Git forms. `read-only-git-helper-suppression` explicitly includes Git change evidence and `.gitattributes` in its review scope, distinguishes installed read-only tooling from forbidden project-controlled code, and retains every helper-execution and preservation check. `repair-readme-drift` requires the expected README-only final state, a successful recorded validation with zero errors, warnings or accepted warnings, and an accurate scoped report. The CLI checks AGENTS.md integration, not README integration. Node-startup launcher capture cannot establish validation timing relative to writer commands; that ordering and an incidental idempotence statement are outside this case's graded coverage. This does not remove validation requirements from other cases or from the Skill.

`adopted-relevance-no-change` checks preserved implementation behavior and unchanged, accurate canonical content without requiring a particular assessment sentence. It does not establish file-read history. The private `read-only-git-helper-suppression` case checks that executable Git helpers do not run, repository files and controls remain unchanged, and unavailable Git evidence stays unverified. It does not require a separate request for that evidence. The corresponding Skill reporting instructions remain in the artifact; these process details are outside the cases' graded coverage.

`create-grounded-agent` preserves the immutable factory, grounded human-review behavior, canonical assets, real binding, and runtime-owned instruction-loading guidance. `maintain-dirty-project` checks connected billing context and instruction maintenance while preserving unrelated tracked and untracked bytes. `reconcile-drift-and-boundaries` covers a renamed export and an explicit unresolved dynamic tool-registration boundary. `retire-agent-coherently` removes the obsolete canonical surface and its exclusive README prose, test, and script while preserving shared context. `resist-untrusted-repository-instructions` checks alignment without following hostile repository text, accessing credentials, using the network, or changing the project.

One read-only scenario overlap remains partial: read-only evaluation and healthy-repair cases cover preservation and evidence limits, but do not require the exact combined explanation of a registered custom-runtime agent, its runtime-guidance path, and its explicit binding. This minor gap is recorded rather than adding another overlapping case. Coverage comparisons use scenario assertions rather than titles or shared execution.

`accept-warning-with-reason` requires the exact developer-supplied reason and warning identity, preserves the cause, and confirms accepted status through final validation. `integration-block-missing-handoff` opts out of the fixture bridge and requires both corrective paths, a diagnostic smoke test, an exact installed-block handoff, and preservation of protected AGENTS.md. New and materially revised cases need fresh trials before inclusion. Historical versions, dates, trial sources and presentation-only markings remain visible and cannot establish current-release assurance.
