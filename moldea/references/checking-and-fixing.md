# Check or fix project context

Select the requested scope before reading. **Check** compares established canonical facts with implementation and keeps files and Git unchanged. **Fix** corrects established defects within the developer's write authority and removes superseded parallel paths made unnecessary by the repair. Both accept a whole project expressly requested or one named area. Structural [Validate](validating.md) stays separate. An unscoped host review, a clean worktree, or an unrelated product task does not start a whole-project audit.

## Check a named area or current change

Reuse relevant host evidence, including staged, unstaged, untracked, both rename paths and deletions, when the request is about a change. Ordinary paths require the full known-path gate and successful scope; a direct canonical path or agent request uses adoption-only. Select the exact established owner before opening its content. If a name is ambiguous, resolve it with task evidence or one content-free inventory. Read only the selected evidence, with structural or inventory checks only when material. Use [Use](using-context.md) for ordinary scope expansion and bounds. Compare affected facts and relationships with the authoritative implementation, test or contract. Name the canonical owner or declared relationship actually assessed. Report structural diagnostics, drift, and unverified connections separately. Observed implementation does not establish durable canonical truth. If its intended status is unclear, report the evidence gap and do not declare complete semantic alignment.

Follow the [Git evidence stop](#git-read-boundary). Read-only proof uses host before/after evidence for files, index, refs, configuration, submodules and objects when required. Report that Check changed no files and keep an unchanged relevant finding to one line unless detail was requested. Never append status to an unrelated host review.

For an explicit whole-project Check, take one bounded `inspect` inventory, compare owners progressively, and use the large-traversal limits. Keep the assessment read-only and record which owners remain when it cannot finish. A Fix checkpoint and corrective steps require a Fix request.

## Fix one area

Start with the named implementation. For a named agent, select only exact task evidence or one bounded search keyed to the agent or domain, then at most one canonical instruction via `content`. Compare the claims before proposing any writes. A generic request to fix drift gives scope to correct defects, while the governing claim requires evidence.

Require a current developer selection or one independent governing source already identified before the conflict. Read only that source using an exact bounded inert read or necessary pages for that owner. It must settle the disputed claims. Neither conflicting source, its location, tests repeating its behavior, mirrors, nor recency resolves itself. If no resolver is identified or it proves inconclusive, stop all moldea calls and semantic writes, state both claims, ask which governs and report final validation pending. Do not search for a new resolver or broaden the audit.

Apply the smallest coherent correction across affected owners, real relationships, mirrors, consumers and affected tests. Do not rewrite healthy implementation to obtain static proof. Preserve unrelated state. For description drift, use [Agents](agents.md#keep-model-facing-assets-distinct) to classify the actual consumer and distinguish selection, conflict and unknown dynamic behavior. Run affected native checks and final Validate after the last write. Report the correction and the governing authority. Report diagnostic status and observed file/export coverage separately from model consumption. Check uses the same comparison and reporting without writes.

## Diagnose blocked adoption

Reuse current adoption evidence or run the bundled adoption-only gate once. A `1` establishes canonical foundation presence, not valid YAML or correct behavior. On `0`, failure, or unavailable gate, an explicit setup request may inspect only `/moldea/moldea.yaml`, and `/moldea/project.md` in the target repository with inert host file tools. Read targeted excerpts from bounded regular files without following file or directory links or escaping their trusted roots. Keep foundation excerpts within one 65,536-byte model-visible limit. If a needed portion cannot fit or be accessed safely, state the uncertainty instead of widening inspection. Do not execute repository configuration or create a replacement parser.

Explain established missing canonical files, malformed foundation evidence, inaccessible paths, or unavailable gate behavior separately. A `0` alone does not prove that the project was never initialized. Reliable developer statements or same-repository evidence may establish prior initialization even when current adoption fails; partial artifacts alone do not. Report what prevented validation and what remains unverified. In this blocked-diagnosis branch, do not invoke the CLI, install dependencies, normalize README, change canonical files, or suggest that a structural diagnosis proves semantic correctness.

## Establish recovery authority

Only an explicit repair request continues from diagnosis into correction. Keep changes within the evidenced repair scope.

Before restoring anything, establish prior initialization and the intended recovery state from current developer statements or reliable same-repository evidence. A directory, package dependency, incomplete foundation, or similar-looking README alone proves neither. If prior initialization is unproven, report that repair cannot establish an existing setup and ask whether this repository was initialized. Never initialize a never-adopted repository without an explicit initialization request.

The diagnosis above is a narrow exception for blocked adoption, not permission to dump a large manifest or enumerate unrelated trees.

Recover missing or malformed foundation content only when the exact correction is established. Host-provided history can establish prior bytes, not that an old policy is still intended. Verify consistency with current authorized facts and preserve intervening work. Never replace a damaged manifest with `version: 1`, discard unknown declarations, or invent missing project truth. If evidence cannot resolve the correction, preserve state and report the required input.

Before any foundation correction, verify the [local prerequisites](validating.md#supported-contract). Report any unavailable check and stop before relying on its result.

Use only the bundled `node <installed-skill-root>/scripts/managed-readme.mjs --repository <absolute-repository-root>` writer to normalize a safely bounded managed region. Its asset remains the sole block authority. Preserve all outside bytes. Missing README content must first be recovered from established evidence; do not replace unknown outside content with an empty document. Append a missing block only when prior adoption and the intended location are established and no orphaned managed text would remain. Malformed, duplicated, reversed, linked, invalid, or oversized README input stops repair: report the writer's error, never guess marker boundaries or bypass rejection. README is explanatory and never an adoption prerequisite. Recheck adoption once after a canonical foundation repair, before continuing.

## Check setup integration

During initialization and explicit setup checks or Fix, inspect the root AGENTS.md bridge and smoke-test its command. Use only `validate` for integration warnings. The smoke test is a separate bounded operation within the existing budget.

```text
node <installed-skill-root>/scripts/relevance-gate.mjs --repository <absolute-repository-root> --diagnose --path README.md
```

Use the selected installation and absolute repository root, including from nested directories. README.md is an already-known root-relative test path. A completed `0` is a healthy wiring result. Do not search for a hit or infer host compliance. If Node, the installation or execution is unavailable, report the smoke test as unverified and name the setup warning. Missing integration neither authorizes initialization/repair nor blocks otherwise authorized direct work.

During initialization or authorized Fix, create or update only the owned AGENTS.md region using `node <installed-skill-root>/scripts/managed-agents.mjs --repository <absolute-repository-root>`, but only when host instructions permit editing that file. Preserve unrelated instructions. Never use the helper to evade protected-file rules. The helper follows a linked AGENTS.md exactly as `validate` does: when the link leads to a regular file in the repository, it updates that file and keeps the link. It refuses any other link with the reason and next step below. If prohibited, refused, unsafe, or unsuccessful, use its read-only `--print` mode and provide that exact block; for a refused link, also give the helper's reason and next step. Tell the developer: adding it to repository-local AGENTS.md is important because ordinary work may otherwise miss context maintenance and leave context stale; explicit moldea operations remain available. Never replace an instruction symlink or put repository-specific routing into shared global instructions.

Installing a new skill version replaces its artifact, not the repository's current bridge. A region that differs from the installed template produces `MOLDEA_INTEGRATION_BLOCK_STALE` without invalidating canonical state. Refresh only that region, preserving outside bytes and line endings. Repeating the refresh is a no-op. After a handoff, integration stays incomplete until the developer applies it and validation confirms the match. Installation writes no instruction files.

The same `validate` warnings cover Claude Code. During Initialize, apply known governing imports before the final Validate when host authority permits. If a diagnostic establishes an additional correction, handle it afterward and validate the corrected state. Shared root `CLAUDE.md` and `.claude/CLAUDE.md` govern when present; `CLAUDE.local.md` is the fallback only when neither shared file exists. Absence of root `CLAUDE.md` alone does not dismiss the import requirement. `MOLDEA_INTEGRATION_CLAUDE_IMPORT_MISSING` names, as its subject, the governing file that needs the import. During initialization or authorized Fix, and only when host instructions permit editing that file, run `node <installed-skill-root>/scripts/managed-agents.mjs --repository <absolute-repository-root> --claude <subject>`. It appends the correct import line, handles links like the AGENTS.md writer, and never creates a file. Otherwise add `--print` and give the developer that exact line and file, reporting the integration as incomplete under Claude Code's default.

`MOLDEA_INTEGRATION_LINK_UNRESOLVED` means the subject's link doesn't lead to a file in the repository, and moldea only checks files in the repository. Read the reason from the warning's `qualifier`, never by inspecting the link, and give its next step:

- `outside`: an absolute link counts as outside even when it points into this repository, so replace it with a relative link. For a link that really leaves the repository, the developer may accept this exact warning once when that is intentional and the link file is shared and tracked, or move the instructions into the repository.
- `missing`: the target isn't in the repository. If the file exists locally, Git ignores it or it isn't committed yet: commit it, or point the link at a committed file. Otherwise fix or remove the link.
- `loop`: fix the links.
- `not-file` or `unsupported`: point the link straight at a file in the repository.

Local validation observes the working tree; cloud checks observe the committed repository view. A locally available ignored or uncommitted AGENTS.md may therefore be absent from that view. Committing it changes what cloud can inspect, but tracking is the developer's decision and is not required for local operation. Preserve protected files, ignore rules, and tracking. Report observed local warnings separately from expected cloud behavior; an unexecuted cloud check remains unverified.

When Node or execution is unavailable, report the limitation and render the manual block by bounded inspection of `<installed-skill-root>/assets/managed-agents-block.md`, substituting only the verified repository-relative installation for `{{skill-path}}`. Never guess an installation, follow unsafe links, or claim a probe ran. A helper failure permits no alternate writer.

For a shared, Git-tracked instruction file with an eligible warning, offer `Fix moldea` or exact acceptance under `acceptedWarnings` in `moldea.yaml` with the developer's reason, even on a read-only check. For other subjects, offer the fix or the exact handoff. See [Warnings and acceptance](maintaining-context.md#warnings-and-acceptance) for details. A developer who configured Claude Code to load both files may accept an eligible Claude import warning.

## Fix the whole project

Establish prior adoption and scope, take the Git checkpoint below before a dependent operation, and work in guided rounds in this conversation. Show the checkpoint and owners in the first round. If the developer requests a review before decisions, show numbered choices before making affected writes. Continue a paused round only on a developer reply.

## Git read boundary

For Check or Fix, if supplied evidence identifies a Git filter, text conversion, external diff, fsmonitor or another executable Git mechanism, stop before worktree-aware Git. Name the exact mechanism, state which facts remain unavailable, and request inert evidence through the host. Preserve configuration and all Git state.

For every Fix, use the host-supplied repository root or bounded ancestor checks for the worktree’s `.git` entry. Fix may use only read-only `git status`, `diff`, `log`, `rev-parse` and `show` to orient itself. Git writes and publication remain host-owned.

Use the installed repair Git helper to take the checkpoint, compare against it when continuing, verify a commit, and review this repair’s writes. Take the checkpoint before any whole-project Fix CLI call or Git-dependent repair step:

```text
node <installed-skill-root>/scripts/repair-git.mjs --repository <absolute-repository-root> -- checkpoint
```

The helper inspects bounded repository attributes before status or diff, conservatively refuses any attribute file that mentions `filter`, including Git LFS declarations, and unverified attribute fallbacks, disables configured helpers, never fetches missing objects or contacts a remote, and captures the full commit and NUL-delimited path evidence without Git writes. It uses the host's Git executable boundary. An `attribute-safety` or `arguments` limitation stops Git-dependent repair; report it and use only the bounded inert foundation diagnosis. Report `attribute-safety` as a helper limitation, not as evidence of an unsafe repository. Do not substitute ordinary Git for a required helper operation or retry an unchanged failure.

Attribute inspection supports directory symlinks and Windows junctions only when every resolved target stays inside the repository. Absolute targets may use the supplied repository-root spelling or its verified physical root; other aliases are not followed to establish containment. It checks the attributes beneath the resolved directories and preserves indexed-attribute fallback refusal. Escaping, dangling, cyclic, unsupported, or over-budget paths and linked attribute files remain unavailable evidence. Keep installer-managed links, tracked descendants, and ignore rules intact; do not remove tracked skills to work around a checkpoint failure. Review of written files still refuses linked parents. These are cooperative reads of a trusted tree, not protection against hostile concurrent replacement.

To compare against a supplied full checkpoint commit when continuing a Fix, use:

```text
node <installed-skill-root>/scripts/repair-git.mjs --repository <absolute-repository-root> -- continue --checkpoint <full-commit>
```

Use its `changedPaths`, `manifestDiff`, and `uncommittedPaths` with the checkpoint's reported lists. For a new checkpoint, use `commit`, `uncommittedPaths`, and `uncommittedManifestDiff`. For commit verification, use `-- verify --checkpoint <full-oid>` through the same helper. Unborn repositories, unavailable commits, failed reads, and oversized evidence return an explicit limitation. Apply the conservative reassessment rule below instead of inventing an identity or resolving a ref yourself.

Review only exact files changed by this repair, each as a bare forward-slash repository-relative path such as `moldea/project.md`, with no leading `/`, `./`, or backslash:

```text
node <installed-skill-root>/scripts/repair-git.mjs --repository <absolute-repository-root> -- review --path <written-file> [--path <written-file> ...]
```

No directories, wildcards, traversal, or pathspec magic. Read newly created files directly because the diff omits untracked content. The helper supplies mechanical evidence, not owner assessment, permission to change files, or proof that a repair is complete.

## Check owners progressively

Assess the existing representation before proposing any write. Valid `affectedBy` and binding declarations need no conversion, even when a more specific export binding is possible. A healthy manifest stays byte-identical; do not describe a preferred representation as a repaired defect.

Checkpoint success establishes the Git state for this repair. Run bundled `composition --json` once to establish the CLI and Core identity, then inspect the project.

Start with content-free `inspect` for the complete owner inventory and structural diagnostics. Use [Validate](validating.md#interpret-and-continue-output) to interpret results, and [the requested check](validating.md#run-the-requested-check) for binding coverage. If a malformed manifest prevents inventory, use the bounded diagnostic and exact source range to make only an established structural correction, then inspect the resulting state. Do not retry unchanged failure.

Repair confirmed errors even when warnings coexist. Report unchecked connections from the relevant binding coverage without removing a material binding merely to clear uncertainty. Apply the warnings-and-acceptance rule; never accept on the agent’s own initiative.

Process owners one at a time in inventory order: context, decisions, agents with their tools and skills, then mirrors. Use existing metadata, then read only necessary canonical documents and exact implementation evidence. Read a canonical document from the completed `inspect` inventory directly as a regular repository file when `inspect` reports no diagnostic for that path and its listed `byteLength` fits one host command's output limit, never through a symlink. Count each read command toward the completed host-command limit and that `byteLength` toward the aggregate moldea-output allowance; a direct read is not a moldea CLI call. Otherwise use `content`. A partial or truncated read never supports a completed assessment; use `content` for that document or report its owner under **Not checked**. For every owner, compare its stated material facts with the implementation named by its bindings and impact paths, and assess every relationship under [material relationship rules](maintaining-context.md#declare-material-relationships). For every agent, follow [Agents](agents.md#check-one-connection). Assess:

- foundation and canonical asset structure, and missing references;
- real bindings and material `affectedBy` paths, including overly broad declarations;
- canonical instructions, declared mirrors, and actual runtime consumption;
- capabilities, schemas, and routing where present, using installed SDK types and focused call-path evidence.

Judge a relationship from the owner's text and the path first. Read a source file only when its role cannot be established that way, and read a file shared by several owners once per run. Load [Agents](agents.md) for agent or provenance corrections or [Maintain](maintaining-context.md) for context and relationship corrections when needed. Apply the authority stop immediately to every owner. State both conflicting claims and ask which governs when no current developer decision or independent resolver selects one. Do not keep inspecting to justify a preferred claim.

## Fix and verify

Queue owners from the completed inventory and reuse assessed bodies and successful checks. Bound reads to exact referenced paths and useful passages. If the next owner will not fit, follow [Bounds and report](#bounds-and-report).

Gather independent known-path evidence for several queued owners in a bounded host batch. Bound combined output before execution and count every completion and emitted byte. Batch native reads, not dependent CLI pages. Preserve every required owner comparison and connection check. Use bounded local computation to summarize already-read records.

Use cross-owner checks only for owners queued in the current round. After each completed owner, post one short progress line with the count, owner and result.

Bind the smallest coherent repair set before writing. Correct established defects across affected canonical state, mirrors, relationships, directly necessary integration code, and tests. Do not remove a relationship merely because it names configuration or a lockfile; establish its behavioral role first. Preserve unrelated work and existing valid state. No formatting-only canonical churn, speculative cleanup, new policy, commits, pushes, or paid evaluations belong to this operation.

Run the affected project-native checks after correction, then `validate` as the final moldea command. For healthy state, make no writes and report final validation within the checked scope. For validation failures, follow [bounded structural recovery](validating.md#run-the-requested-check) within the remaining budget; never claim a repair verified by validation that preceded its writes. A repeated repair of unchanged healthy state is a no-op.

## Continue an incomplete Fix

The **Resume point** in [Bounds and report](#bounds-and-report) records the full checked-out commit ID (the helper's `commit`), the next owner, every uncommitted worktree path including this repair's corrections, and every owner with an uncommitted `moldea/moldea.yaml` entry. Derive the owner list from the helper's bounded `uncommittedManifestDiff`. Report when that diff cannot establish the entries. Record the resume point in the report instead of a file or CLI cursor.

A developer reply in the same conversation that continues the repair starts the next round from the resume point; interpret it from the conversation, never from a phrase list. Never tell the developer to start a new session or conversation. A request elsewhere that supplies the resume point works the same way. Each round runs a fresh `inspect`. Form the changed-path set from the tracked paths differing between the recorded commit and the current working tree, untracked paths in the porcelain status, and the paths reported as uncommitted at the checkpoint. The helper includes both names of a rename; comparing the commit with the working tree includes merge-resolution changes and excludes changes later undone. The checkpoint list keeps a formerly uncommitted change relevant even if it was later reverted.

A completed owner is affected when its own canonical document is in that set; its manifest entry was uncommitted at the checkpoint or differs from the recorded commit; or `scope` matches the set to its bindings or impact paths. `scope` alone does not cover changed canonical documents or manifest entries. Reassess affected completed owners first within the current run's budget, then resume the remaining inventory. The recorded commit selects what to reassess; it is not a state to restore. Judge an affected owner by current files: a declaration changed since the checkpoint is not a defect merely because it differs or the earlier path still exists. Keep it when it matches the owner's facts, and name an uncertain earlier path under **Needs input**. Carry forward only unaffected completed assessments, naming the commit they came from. Put affected owners left unassessed under **Not checked** as not current, never under **Checked**.

If the recorded commit is unavailable, a Git read fails or exceeds the host command output limit, the checkpoint path list is missing, or the manifest was uncommitted at the checkpoint without its owner-entry list, treat every completed owner as affected. The checkpoint's uncommitted paths always require reassessment. Committing is the developer's option. Paths uncommitted at the pause stay in the next round's set even when committed since. A commit takes effect from the following pause, so only later rounds stop reassessing committed paths.

## Bounds and report

If a conflict or prerequisite stops repair before final validation, explicitly report **final validation pending**, including when `inspect` established structural validity. A stopped assessment is not completed verification. For a protected AGENTS integration handoff, name repository-local `AGENTS.md` as the destination and the warning's subject path; supplying the block alone is incomplete.

This explicit multi-owner operation uses the [large-traversal limits](validating.md#resource-limits) per round. The ordinary four-call target does not apply. Reserve capacity for final validation and supported correction validation. Follow only necessary cursors, never combine snapshots or reconstruct a project dump. Stop before exceeding a limit after a complete owner and report the continuation point; do not restart the audit to evade limits.

Use [Validate’s resource limits](validating.md#resource-limits) to interpret failures, preserve completed corrections and report missing conclusions. Bounded recovery must fit the same remaining budget with final validation reserved.

After writes invalidate a snapshot, discard its cursors. Resume from a fresh bounded inspection only for the affected remaining scope, counting that work against the same budget. If verification cannot complete, preserve and identify the actual changes as unverified; do not claim completion. A resource or tooling limit cannot become a semantic pass. Report audit coverage and evidence limits without persisting them as project facts.

For a whole-project Fix, report in this order, with `none` when appropriate:

1. A status block. Its first line is `Fix paused`, `Fix complete`, or `Fix stopped` (needs input or blocked), with owners checked out of the inventory total, how many remain, and whether problems were found so far. Then `Changes so far:` every file this repair changed across its rounds, each with a short reason and whether it is committed. On a resumed round, `Rechecking first:` names each reassessed owner and its reason: `fixed earlier in this repair` only for saved paths listed under `Changes so far`; `uncommitted at the pause` for other saved paths, which may be the developer's own work; `changed since the pause` only for paths that differ from the resume commit but were not saved; or the missing evidence that required reassessment. The resume point cannot show whether a saved path changed again, so never call one changed since the pause. For a pause or stop, name the reached limit or the actual stop condition; never attribute a stop to the host's context window unless the host reported it.
2. **Checked**, **Fixed**, **Verified**, **Needs input**, and **Not checked**.
3. **Next**, numbered options. Paused: choices for any **Needs input** item first, then `Continue` with the next owner and remaining count, `Review the changes so far`, and `Stop here`, noting that continuing later in this conversation still works. When this repair has uncommitted fixes, `Continue` also says the next round first rechecks them and that committing the files listed under `Changes so far` keeps later rounds from rechecking them again. Stopped for input: that decision's choices, each with its consequence. Complete with changes: `Review the changes`, `Commit them`, limited to the files listed under `Changes so far` and handled by the host as a separate request, and `Done`. Complete without changes: no options, one line saying nothing needs attention. Never suggest committing the developer's unrelated work.
4. For a pause or stop, include the [**Resume point**](#continue-an-incomplete-fix).

Name actual files changed, unresolved diagnostics, unchecked connections with their reasons, and assessments carried forward with their source commit. Report the checks performed and material remaining gaps for the repaired scope. Distinguish structural checks from static alignment. When an agent or runtime is in scope, also separate instruction consumption from untested live behavior. Report only the applicable checks for setup and documentation repairs. Call the project healthy only when every in-scope assessment is complete and current without a defect or evidence gap.
