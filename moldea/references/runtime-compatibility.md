# Runtime compatibility

Read this reference after relevance is established when runtime selection, package eligibility, source-pattern support, or runtime readiness matters. Resolve ordinary compatibility locally; do not retrieve compatibility websites, open browsers, or use network clients for this workflow.

## Use the fixed evidence sequence

For a direct evaluation of one named agent and target, invoke `composition` first and retain its conclusion. Composition establishes local executable availability, never canonical assignment. When supplied evidence does not already establish the exact `agents.<agent-id>.runtime.id`, use one content-free `inspect`; the matching `kind: agent` record's exact `agentId` and `runtimeId` are the sole canonical content-free source for that assignment. Then request at most one named agent body only when its semantics matter. Never infer assignment from top-level runtime counts or guidance, request `/moldea/moldea.yaml` through `content`, guess canonical paths, add `inspect` after a content attempt, or request a second canonical body.

Reuse current local inspection diagnostics and evidence for the selected adapter and bound source. When a material compatibility fact remains unresolved, read the installed adapter's README, then only its specifically relevant linked local guide. Reuse those instructions under the entrypoint's reference-read policy. Do not read every guide or discover the package again when its installed location is already established.

Inspect the relevant repository package declaration or lockfile entry for version evidence. Read adapter implementation only when diagnostics and its documentation cannot resolve a specific material question; name that question and inspect the smallest owning source. Missing documentation is an evidence gap, not proof of incompatibility or permission to choose `custom`. Do not enumerate dependencies or dump package trees. Direct relevant work remains inside the ordinary four-command moldea limit, except for the route-5 fifth-call repair validation defined by the entrypoint.

## Keep the evidence boundaries separate

1. Canonical moldea declarations establish the declared runtime identity and relationships. A top-level runtime inventory or `inspect.project.runtimes` count cannot negate an agent assignment.
2. Repository source, configuration, closed wiring, source-owned contracts, and focused integration tests establish actual behavior and behavioral fit.
3. Root-local `composition --json` establishes the installed executable, active adapter IDs, package versions, repository-format versions, and Node.js and Git requirements. It proves availability only.
4. Installed adapter contracts and deterministic inspection establish package eligibility, recognized source patterns, and specific limitations for that installed implementation. Absence of diagnostics alone does not prove behavioral fit or support for uninspected source.

The packages website is a discovery and reference catalog, not a runtime prerequisite. Website presentation labels never affect runtime identity, eligibility, or unresolved state. Missing online information cannot erase independently established local facts or block eligible local inspection.

## Make runtime claims precisely

- Select the highest-level official adapter that matches the actual primary model-invocation boundary and is available locally. A package name or adapter inventory alone is insufficient.
- A target package range is a best-effort eligibility gate, not a blanket compatibility promise. Its lower bound records the verified minimum. Stable versions satisfying the installed adapter's range remain eligible for source-pattern inspection, including later stable releases that were not themselves used in qualification. For example, Eve `0.54.3` satisfies `>=0.39.1`; it does not need a new published verification date before local inspection.
- Qualification proves only the exact package closure and verification date recorded by that attempt, not every eligible version.
- If a package range excludes the repository's selected provider version, report the exact local mismatch and preserve the runtime identity. Do not remove a real mismatch or fabricate a compatible range to proceed.
- If the adapter is absent, report the local tooling prerequisite. Do not dynamically install an adapter or replace the CLI closure outside the local-tooling contract.
- `custom` is a deliberate project-specific runtime, never a fallback for missing evidence, an incompatible package version, an unavailable official adapter, or an online lookup failure.

For behavioral fit, identify material model API and control flow, instruction loading, tools and schemas, continuation, state and handoffs, error and retry semantics, lifecycle, and persistence. Pair each unknown with a concrete reliable resolver: current source contracts, closed wiring, source-owned target documentation, or focused integration tests. Preserve the canonical runtime when an evidence gap prevents a change.

Report canonical identity, repository fit, local adapter availability, and locally established eligibility or limitations separately. Scope readiness to inspected evidence, never a blanket production guarantee. When changing `runtime.id`, retain every independently evidenced model-visible capability in canonical guidance. Do not run `validate` when structural status cannot change the runtime conclusion.
